# ADR 0001：P0 工程与空宿主基线

- 状态：已接受；验收结果以实际检查记录为准。
- 日期：2026-10-28。
- 适用阶段：P0。
- 相关文档：[架构入口](README.md)、[安全边界](security.md)、[兼容性矩阵](../compatibility/README.md)、[整体设计](../../SKILL.md)。

## 背景

仓库从 Rust 初始化程序进入 P0，需要先建立可构建、可启动、可停止且不依赖任何插件的最小宿主。P1 以后才引入插件进程、wire 类型和管理接口；提前创建没有行为的 crate 会增加维护成本，也容易让目录结构被误读为功能完成。

## 决策

### 工程与工具链

采用虚拟 Cargo workspace，根清单仅承担 workspace 配置，resolver 固定为 `3`。唯一成员为 `crates/twintail-host`，包和二进制名均为 `twintail-host`，使用 Rust edition `2024`。P0 不建立空的 `twintail-core`、`twintail-protocol` 或 SDK crate。

Rust 工具链与当前最低支持版本（MSRV）均为 `1.99.1`；工具链文件和 Cargo 的 `rust-version` 保持一致。CI 使用同一版本，不以 Rust 2024 的理论最低版本替代本项目的支持承诺。后续降级或升级 MSRV 必须经过依赖与平台验证，并同步清单、工具链、CI 和文档。

### 空宿主生命周期与 CLI

Tokio 提供异步运行时和停止信号等待。P0 命令语义如下：

| 调用 | 预期行为 |
| --- | --- |
| `twintail-host` | 完成启动检查、显示运行路径并持续运行，直到收到支持的停止信号 |
| `twintail-host --check` | 完成启动检查并显示路径后成功退出，不进入持续等待 |
| `twintail-host --help` | 显示使用说明并退出 |
| `twintail-host --version` | 显示宿主版本并退出 |
| `twintail-host --data-dir <PATH>` | 设置数据根路径；可与 `--check` 一起使用 |
| `twintail-host --install-dir <PATH>` | 设置安装根路径；可与 `--check` 一起使用 |

所有平台支持 Ctrl-C；Unix 额外等待 SIGTERM。信号等待设施建立失败应报告启动错误。P0 没有插件、监听器或业务任务需要排空，退出能力不代表已经实现未来插件的优雅停止流程，也不承诺处理 SIGKILL 等不可捕获信号。

`--check` 检查本阶段启动条件及参数处理，不校验未来配置、插件包、目录存在性或写入权限，不连接 SnowLuma 或网络服务。检查成功不代表已具备完整机器人运行环境。

### 路径与配置

| 参数 | 默认值 | 相对路径的基准 |
| --- | --- | --- |
| `--data-dir` | `./data` | 进程当前工作目录（cwd） |
| `--install-dir` | `./packages` | 进程当前工作目录（cwd） |

两个参数接收路径值，可使用绝对路径。它们不以可执行文件目录、源码根目录或用户主目录为默认基准。带空格的路径按调用 shell 的规则引用，例如 `--data-dir "./local data"`。

P0 仅解析并显示路径，不读取或写入路径内容、不创建目录、不加载 `host.toml`、插件清单或任何配置。显示相对 cwd 解析得到的路径不等于文件系统规范化，也不构成目录边界校验；P0 不要求路径已经存在。`..` 等用户提供的根路径组成部分与未来插件 id 是不同输入，插件 id 的约束不能直接用来替代根路径参数语义。

后续布局将安装包与运行数据分开：安装根存放版本包，数据根承载宿主配置、插件配置与私有数据、秘密引用及审计等。该布局是设计目标，P0 不在磁盘创建它。

### 后续插件身份与包路径约束

插件 id 的后续契约为 `^[a-z][a-z0-9._-]*$`：首字符必须是小写 ASCII 字母，其余字符仅允许小写 ASCII 字母、数字、`.`、`_`、`-`。大写、非 ASCII、斜杠、反斜杠、空值及首字符为数字的 id 均不接受。id 是逻辑身份，不作为任意文件系统路径使用；不得允许目录穿越。

P0 没有插件清单解析器或安装器，尚未执行上述校验。未来包内入口、解包目标和资源路径必须验证规范化后的实际目标不越出对应包根，拒绝目录穿越、绝对路径绕过与越界符号链接；Windows 还需考虑驱动器、UNC、路径前缀和重解析点等平台行为。单纯字符串前缀比较或 id 正则不能证明实际路径安全。实现时还需处理校验与使用之间的路径替换风险。

Unix 权限及 Windows ACL 的创建、校验和修复属于后续安全实现目标，不能将 P0 路径显示解释为已有权限隔离。详见[安全边界](security.md)。

### CI 与验证

CI 计划在 Linux 和 Windows 上使用 Rust `1.99.1`，执行以下基础检查：

```sh
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo doc --workspace --no-deps
cargo run -p twintail-host -- --check
```

文档检查将 `RUSTDOCFLAGS` 设置为 `-D warnings`；环境变量采用对应 runner 的 shell 语法。CI 以 `--check` 验证有界的启动退出流程，不直接运行会一直等待信号的默认命令。默认驻留、Ctrl-C 与 Unix SIGTERM 需要独立的生命周期验证。

配置工作流不等于平台检查已通过；Linux/Windows 的远端 CI 均在真实运行前标为“待执行”。本地检查结果也不替代另一平台的验证记录，状态统一见[兼容性矩阵](../compatibility/README.md)。

## 取舍与影响

单二进制成员让空宿主的职责和依赖保持可审查，之后可以随真实接口拆分核心与协议 crate。固定工具链有利于复现，但依赖升级必须尊重 MSRV。默认驻留为后续宿主生命周期提供基线，自动化检查使用 `--check` 避免等待交互信号。

P0 明确不实现插件加载、安装、IPC、能力授权、配置解析、秘密存储、OneBot/SnowLuma 对接或 WebUI。后续安全机制和外部兼容性需分别实现并验证，不因本 ADR 被接受而视为交付完成。
